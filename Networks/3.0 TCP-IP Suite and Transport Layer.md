## Checksum
Error method used by TCP/IP
- protects against corruption during transmission
- added to TCP header
![[Pasted image 20260912193524.png]]

Sender:
1. Packet is fragmented into n sections of k bits each
2. Packets are processed with ones complement arithmetic and complemented to create the checksum

Receiver:
1. Packet received in n sections of k bits each
2. Addition via ones complement arithmetic
3. summed to provided checksum and complemented

If result yields all bits are 0 Data is uncorrupted!

\* **ones complement arithmetic** - a process where overflow from sum of each segment onto result is wrapped and used as next addition
![[Pasted image 20260912193915.png]]

\* all higher order functions have their individual checksum fields covering the entire packet
- checksum in IP only covers changes in IP header, not the original data
- checksum in TCP / UDP cover end to end integrity and involve checking actual data
*saves processing power, eg for router*

## Transport Layer
**Transport Protocols**
- **User Datagram Protocol** - minimal overhead, unreliable communication	
- **Transmission control protocol** - reliable, ordered, error checked delivery of data between applications over a network
### UDP data
Minimal overhead, unreliable communication.
- connection less
- unreliable
- fast and efficient: small 8 byte header

3 sections - pseudo header + UDP header + data
- data is always padded to be 16 bits
\* eg: video conference

### TCP
reliable error checked delivery of data between applications over a network
**ACK** - Next expected byte number
**SYN** - Seq number of first byte of data in TCP stream 

**Connection establishment** - Three way handshake
1. Client sends a SYN request to the server
2. Server acknowledges start of communication and replies with a SYN ACK
3. Client replies with ACK to acknowledge receipt
![[Drawing 2026-09-12 20.03.19.excalidraw]]

**Connection termination** - Three way Termination and Four way Half Close Teardown

*Three way Termination*
1. Client sends FIN
2. Server confirms receipt of FIN and announces closure
3. Client replies with ACK
![[Drawing 2026-09-12 20.12.10.excalidraw]]

*Four way Half Close Teardown* - One end stops sending while still receiving data
- both sides can issue the request
- second FIN not immediately generated
![[Drawing 2026-09-12 20.16.21.excalidraw]]

\* sequence number: first byte's sequence number in any particular sequence
